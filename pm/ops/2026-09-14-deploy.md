# 11:00~11:30 第三次回填：时钟「挂了但没跑」，已换 schtasks 兜底

## 9.5 ⚠️ `quant-prod-clock` 注册成功但**一tick 没跑**（根因已定位）

11:00~11:20 复核发现：cron 作业 `e22a101a`（`quant-prod-clock`）**连续 4 次 `status=skipped / error=disabled`**，
`prod_clock.log` 里 10:50 之后**没有任何新增 tick**（11:00 / 11:10 两档全空）。

**根因（从 OpenClaw 源码 `dist/heartbeat-runner-*.js` 定位，不是猜测）：**

```js
if (!areHeartbeatsEnabled())            return { status: "skipped", reason: "disabled" };
if (!isHeartbeatEnabledForAgent(cfg, agentId)) return { status: "skipped", reason: "disabled" };
if (!resolveHeartbeatIntervalMs(...))    return { status: "skipped", reason: "disabled" };
```

`sessionTarget="main"` + `payload.kind="systemEvent"` 的 cron，**不是直接 exec**，而是走「注入心跳事件 → 让 main session 的 agent 在心跳里执行」这条路。
而本产机 `openclaw.json` 里**没有配 `agents.defaults.heartbeat`**（无 `every`、无 `activeHours`），`HEARTBEAT.md` 也是空清单 → `resolveHeartbeatIntervalMs` 返回空 → 心跳判定 `disabled` → **tick 被静默丢弃**，`wakeMode=now` 也救不回来。

也就是说：**DEPLOYMENT 文档里「systemEvent 通知主会话」这条路，在本机心跳未启用的前提下是走不通的。** 这不是脚本问题，是运行时机制问题。

## 9.6 ✅ 已换 schtasks 兜底：`QuantLearn_ProdClock`

  /tr "C:\Users\Administrator\.openclaw\workspace\quant-learn\scripts\prod_clock_runner.bat" ^
